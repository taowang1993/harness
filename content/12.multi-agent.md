---
title: "Multi-Agent Architecture"
description: "How sub-agents are isolated, coordinated, and surfaced across different coding-agent products."
---

Sub-agents are one of the clearest places where product philosophy shows up.

## Codex: In-Process Agent Tree

Codex has built-in sub-agents running as async tasks with shared process state.

## DeepSeek Harness: Provider-Based Durable Subagents

DeepSeek Harness exposes subagents through a provider seam. Its shipped in-process providers can spawn a fresh child or fork a completed prefix of the parent's durable history.

### Characteristics

- spawned children start fresh
- forked children receive a completed durable-history prefix
- children may be one-shot or continuable
- continuable children retain durable sessions
- in-process children inherit the parent's agent preset and a fixed delegated permission scope
- workflows can fan out children under concurrency and total-agent limits
- external ACP, CLI, and DSH SDK providers can use separate runtimes

### Tradeoff

The provider seam supports both lightweight in-process children and externally isolated runtimes, but workflow script state itself is not checkpointed and cannot resume after interruption.

## OpenCode: Child Sessions via the `task` Tool

OpenCode has a built-in multi-agent model, but it is neither Codex-style async tasks nor DeepSeek Harness's provider-based spawn/fork model.

### Characteristics

- primary agents like `build` and `plan`
- subagents like `general` and `explore`
- `task` tool launches or resumes **child sessions**
- task permissions control which agents another agent may invoke
- child sessions can be navigated from the UI as part of the session graph
- the whole system runs inside the same overall runtime/server instance

### Tradeoff

This gives OpenCode stronger built-in orchestration than Pi and a more UI-centered session graph than DeepSeek Harness, whose isolation depends on the selected subagent provider.

## Pi: No Built-In Sub-Agents by Design

Pi intentionally omits built-in sub-agents.

Instead you can:
- run multiple pi instances
- use tmux
- spawn sessions from the SDK
- build a sub-agent tool or workflow with extensions

## Hermes: `delegate_task` Child Agents

Hermes has a built-in delegation model centered on isolated child agent instances.

### Characteristics

- `delegate_task` spawns child `AIAgent` instances
- each child gets a **fresh conversation**, not inherited history
- each child gets its **own terminal session** and restricted toolsets
- only the final summary flows back into the parent context
- up to 3 children can run concurrently in common batch mode
- depth is intentionally limited and several tools are always blocked for children

### Tradeoff

Hermes gives you stronger built-in delegation than Pi and stronger default context isolation than OpenCode; unlike DeepSeek Harness, it fixes that delegation model rather than exposing a provider seam.

## Comparison

| Aspect | Codex | DeepSeek Harness | OpenCode | Pi | Hermes |
|--------|-------|------------------|----------|----|--------|
| **Built-in sub-agents** | Yes | Yes | Yes | No | Yes |
| **Isolation model** | async tasks | provider-defined; shipped spawn/fork providers run in process | child sessions in same runtime | user-defined | child agent instances with fresh context and separate terminals |
| **History sharing** | forked parent history | fresh spawn or completed durable-history prefix on fork | separate child session with inherited context rules | user-defined | explicit `goal`/`context` only |
| **Navigation** | internal | durable child sessions and lifecycle events | explicit child-session navigation | user-defined | summary/progress oriented, not session-graph oriented |
| **Opinionation** | High | High defaults with a replaceable provider seam | High | Deliberately low | High |

## Takeaway

OpenCode is the open-source system here with the most built-in multi-agent product surface.
Pi is the one that most strongly refuses to choose a sub-agent model for you.
Hermes is notable because it chooses a very practical middle ground: built-in delegation with fresh-context child agents and separate terminals, but without turning multi-agent work into a full session-graph UI.
